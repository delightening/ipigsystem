# 派工 Prompt 模板（TEMPLATES）

> 配合 `DISPATCH.md` 使用。`{...}` 是填空；【】內是給主模型的填寫指引，發出前刪掉。
> 每份模板已內建三件套（目標動機 / 驗收條件 / 回報格式）與回報合約。

## 通用尾段（每個派工 prompt 結尾都附上）

```
工具規則：用 Glob 找檔案、Grep 搜內容、Read 讀片段。**不要用 bash find/grep/cat/ls/head/tail**
——subagent 不繼承主 session 的 Bash deny 清單，用了會繞過使用者的安全設定（2026-07-04 稽核實證：
兩個 agent 這樣繞過了 find 的 deny）。唯讀搜尋一律走專用工具。

回報規則：
- 只回結論 + 證據位置（檔案:行號），不要貼整檔或大段程式碼。
- 產物 >20 行一律寫檔，回傳完整路徑。
- 最後必答：(1) 你檢查過但沒有問題的範圍 (2) 不確定的地方（沒有就寫「無」）。
- 摘要 ≤30 行。
```

---

## 1. 搜尋 / 定位（agent: Explore，model: sonnet）

```
目標：找出 {要找什麼，例如「所有直接寫 SQL 的 handler 函式」}。
動機：{為什麼找，例如「要評估遷移到 repository 層的工作量」}——邊界情況照這個動機取捨。
範圍：{目錄 / glob，例如 backend/src/handlers/**}。
搜法：至少用兩種角度（{例如：by-name 搜函式名 pattern、by-content 搜 sqlx::query}），
兩種結果要互相對照，只有一種搜法找到的條目要標註。
驗收條件：每個結果附 檔案:行號 + 一行說明；明說你用了哪些 pattern 搜、掃了哪些目錄。
回傳格式：清單（位置 | 一行說明 | 哪種搜法找到）。若 >30 條，寫入 {scratchpad 路徑}/search-result.md 回傳路徑與計數。
```

## 2. 實作（agent: general-purpose，model: sonnet；已驗證 pattern 的批次套用降 haiku）

```
目標：{做什麼，一句話}。
動機：{為什麼做——讓你在規格沒寫到的細節上做出和需求方一致的選擇}。
先讀：CLAUDE.md 路由表指到的規則檔（{RULES_BACKEND.md 或 RULES_FRONTEND.md}）＋{相關既有實作範例 檔案:行號}。
規格：{明確步驟或 pattern。批次任務逐檔列出：檔名 → 要改什麼}。
禁區：不動 {列出不許碰的檔案/區域}；diff 不得包含與本任務無關的 hunk。
驗收條件（全部要有證據）：
- {測試指令，例如 rtk cargo test --lib} 綠。
- {批次任務加：逐檔 rtk grep 確認 pattern 已套用，列出每檔命中行號}。
回傳格式：改了哪些檔（檔案:行號 + 一句話）、驗收指令的實際輸出結尾、沒改的檔與原因。
```

## 3. 重構（agent: general-purpose，model: sonnet）

```
目標：{重構什麼 → 變成什麼形狀}。行為不得改變。
動機：{為什麼值得動，例如「同一 SQL 出現 4 次，違反 repository 規則」}。
基線：先跑 {測試指令} 記錄 green 清單，貼在回報開頭；紅的測試先回報，不要開始重構。
步驟：{小步驟清單，每步可獨立驗證}。
驗收條件：基線測試全綠不變；無新增 clippy/eslint warning；diff 中每個 hunk 都屬於重構本身
（發現順手想修的別的問題 → 記到回報的 Follow-up 段，不動手）。
回傳格式：基線結果 → 每步做了什麼 → 終態測試結果 → Follow-up 清單。
```

## 4. 研究 / 查證（agent: general-purpose，model: sonnet；結論將決定架構時用 opus）

```
問題：{要回答的具體問題，是非題或選擇題最好}。
動機：{這個答案會決定什麼}。
來源優先序：{官方文件 / repo 內既有實作 / changelog}＞部落格；每個關鍵結論附來源 URL 或 檔案:行號。
驗收條件：結論明確可執行（不是「視情況而定」）；訓練記憶與來源衝突時以來源為準並標註；
查不到的部分明寫「查無」，禁止編造版本號 / API 行為。
回傳格式：結論（≤5 行）→ 依據（來源清單）→ 反面證據或風險 → 查無清單。
完整筆記寫入 {scratchpad 路徑}/research-{主題}.md。
```

## 5. 審查（agent: general-purpose；常規 sonnet，安全類 opus——碰權限 / audit / migration / secrets 任一即算安全類）

```
對象：{diff 範圍或 PR 號；或 檔案清單}。
動機：{在找什麼等級的問題——「會壞的」還是「可以更好的」；審查嚴度照這個定}。
審查維度（逐項回答，沒問題也要寫「查過，無」）：
1. 正確性：{該功能的具體失敗情境，例如「權限繞過：非 view_all 角色能否讀到別的計畫」}
2. 本專案紅線：unwrap/unwrap_or on DB、handler 直寫 SQL、硬編色彩、Zod/eval、audit 路徑遺漏
3. {任務特定維度}
驗收條件：每個 finding 附 檔案:行號 + 觸發情境（什麼輸入/狀態 → 什麼錯誤結果）；
無法構造觸發情境的 finding 標為「疑慮」不算 finding。
回傳格式：finding 清單（嚴重度排序）→ 各維度「查過無問題」聲明 → 疑慮清單。
```

## 6. 驗收（fresh-context，agent: general-purpose，model: sonnet；高風險 opus）

> 注意：prompt 裡**不要**描述實作過程，只給產物與標準，避免驗收者被實作者的敘事帶走。

```
請驗收以下產物（你沒有參與製作，請以懷疑態度讀）：
產物：{檔案路徑 / diff 範圍}。
它聲稱做到：{逐條列驗收條件}。
請逐條回答：達成 / 未達成 / 無法判定，各附證據（檔案:行號 或 指令輸出）。
另外回答：(1) 有沒有自相矛盾或與 {CLAUDE.md / RULES_*.md} 衝突之處
(2) 一個弱模型照著它執行，最可能誤解哪一句。
```
