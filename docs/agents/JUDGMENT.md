# 判斷力外化（JUDGMENT）

> 何時讀本檔：你在猶豫——要不要升級模型、算不算完成、要不要問使用者、該不該換路、品質夠不夠。
> 每條判準附正例（✅ 該這樣）與反例（❌ 不該這樣）。例子多取自本專案真實事件。
> 撰寫：2026-07-04（Fable 5）。

## 1. 何時該升級模型（或找第二意見）

**判準**：問題的難點從「執行」變成「判斷」時升級。執行 = 步驟明確只是量大；判斷 = 需要在
互相衝突的證據或方案間裁決、或錯了會誤導後續一連串工作。

- ✅ 正例：兩個 subagent 對「這個 403 是 geofence 誤觸還是真 IDOR probe」給出相反結論
  → 這是判斷題，升 opus 帶雙方證據裁決（2026-06-11 geofence 事故正是誤判代價的示範：
  誤判導致全院共用 IP 被自動封鎖）。
- ❌ 反例：haiku 批次改 10 個檔案，其中 1 個檔案結構特殊改壞了 → 這不是「難」，是該檔超出
  pattern，把該檔單獨升 sonnet 即可，不需要整批升 opus 重做。

**量化觸發**（見 DISPATCH.md §6）：haiku 錯 1 次升；sonnet 同一子任務錯 2 次升並帶完整失敗軌跡；
任何模型同一 prompt 不重派第三次。

## 2. 何時算「真的完成」

**判準**：完成 = 驗收條件逐條有證據，且證據不是自己的宣稱。最低證據等級：
程式碼 → 對應層級測試綠（RULES_BACKEND §7）；新產出的制度 / 規格 / 交付文件 → fresh-context
read-back 通過（例行小更新如 TODO 打勾、PROGRESS 加一條，不需派驗收）；
部署 → 健檢 endpoint 實際打過；「找完了」→ 換一種搜法零新發現。

- ✅ 正例：修 leave 審批死鎖 → 先寫 reproducing test 確認紅 → 修 → 綠 → `cargo test --all-targets`
  全綠 → 回報時附測試名稱與結果。
- ❌ 反例：「我已把 GuestHide 包到 10 個檔案的按鈕上」但沒跑 tsc 也沒抽查——歷史上 codex 批次
  改檔就漏過檔案。批次改檔的完成證據 = 逐檔 grep 確認 + tsc 零錯誤，缺一不可。

**特別條款**：
- 測試紅 = 未完成，沒有例外。不可用「測試環境問題」帶過——除非能指出具體 flake 證據
  （如 CI setup-rust <2min 早夭這種已知 pattern）。
- 「完成 90%，剩收尾」不是完成。回報時寫明剩什麼、誰做。

## 3. 何時該停下來問使用者

**判準**：滿足任一 → 問：(a) 動作在 CLAUDE.md「必問紅線」清單上；(b) 多個合理方案，
選錯的代價 > 問一次的代價，且無法從現有文件/記憶推出使用者偏好；(c) 任務缺成功標準；
(d) 你即將做的事和使用者字面要求不同。

- ✅ 正例：使用者說「把報表匯出加上 X 欄」，你發現該報表有兩個版本（列印版 / 匯出版）且行為
  應該不同 → 問（一句 auq 就能省掉整輪返工）。
- ❌ 反例：「檔名要叫 `report_utils.rs` 還是 `report_helpers.rs`」→ 不問，自己挑一個符合
  既有慣例的（`utils` 已存在同型檔就跟隨），這是低風險可逆決策。

**反向判準（不要濫問）**：使用者離開時（autonomous 模式）問 = 阻塞整個任務。可逆 + 順著原請求
的事直接做；只有紅線和真正的 scope 分歧才停。批次任務完成一項自動下一項。

## 4. 方向錯了的訊號（換路，而非更用力重試）

**判準**：出現以下任一訊號，停止在原路上加力，回到上一個分岔點：
- 同一個錯誤修了兩次還在（修的是症狀不是根因）。
- 每修一處就冒出新的破損處（改動面在擴散 = 切入點錯了）。
- 你開始需要「特例中的特例」（if 裡面第三層 if 處理邊角）。
- 修法開始違反本專案既有紀律（要加 `#[allow(...)]`、要跳過測試、要 hack CSP）。
- 解釋不了為什麼會好（「反正現在綠了」）。

- ✅ 正例：標楷體在 WeasyPrint 破字 → 試 fontTools 失敗、試 freetype decompose 失敗 →
  第二次失敗後停下重新定性問題（「是 subset 弄壞 composite」），換 fontforge unlinkReferences
  一次解決。連續失敗後**重新定性問題**，而不是試第三個 decompose 工具。
- ❌ 反例：session idle 踢人 → 改了 `session_timeout_minutes` 沒效 → 把它改得更大 → 還沒效 →
  再加 buffer……實際上有兩條獨立路徑（DB session + refresh token env），第一次「改了沒效」
  就該觸發「我的因果模型錯了」而不是加大劑量。

**換路的動作**：寫下當前假設為何被否證 → 列出還沒排除的假設 → 選代價最低的驗證實驗。
這正是 `/systematic-debugging` 的流程，卡住兩輪就切過去。

## 5. 品質底線怎麼驗（最低可執行清單)

commit 前逐條過（不是感覺過）：
1. `rtk git diff` 每個 hunk 都能對應使用者請求的某句話？對不上的 hunk 刪掉。
2. 對應層級的測試/檢查跑過且綠（後端 RULES_BACKEND §7；前端 tsc + eslint）？
3. 動到信任邊界（輸入驗證、權限、audit）？→ 該路徑有測試覆蓋，不能只靠人眼。
4. 新增的字串使用者看得到？→ 走 i18n `t()`，且 zh/en 都有。
5. 數字門檻（函數 ≤50 行等，見 CLAUDE.md）沒超標？
6. 回報裡的每個「已完成」都有可指認的證據（測試名 / 檔案:行號 / 指令輸出）？

## 6. 誠實條款：這套制度補不了的東西

拆解、驗證、多樣本評審能補**執行品質**；以下兩類補不了，遇到就照寫的做，不要假裝能：

- **模糊題**（需求本身未定形：「這個功能該長怎樣」「這樣算不算過度設計」）：
  制度性動作 = 產出 2–3 個具體選項（可用 HTML 預覽 / 表格對比），標各自代價，交使用者裁定。
  不要讓弱模型自己「選一個感覺對的」。
- **品味判斷**（視覺美感、文案語感、API 人體工學）：
  制度性動作 = (a) 先查 DESIGN.md / 既有 pattern 有沒有先例，有就跟隨；
  (b) 沒有先例 → 產預覽讓使用者選（本專案已確立的做法：UI 改動先產圖）；
  (c) 使用者不在 → 選最保守、最像既有系統的那個，並在回報中標明「品味決策，未經確認」。
- 兩類共同的禁手：**不要用流暢的語言把不確定包裝成確定**。「我選了 A」必須伴隨「因為 B；
  若你偏好 C 改起來成本是 D」。
